Shared Memory (open-source memory framework for coding agents) · sufficiency pilot, cost leg · measured 9 November 2026

What it costs to ask a small model whether search found the answer

When a coding agent searches Shared Memory, the returned records may match the query wording without containing enough information to answer the question. Checking that property, called sufficiency, requires a separate judgement. GLiNER2.5-Decide (Decide), a small local classifier that outputs a probability for whether a passage satisfies a condition, judged real-length memory searches on a desktop CPU and on an Intel Arc Pro B70 through two GPU backends. The card answers a typical search in 0.663 seconds, while the CPU needs 44.2 seconds. This page sets out the setup, the numbers, how far they can be trusted, and how the next study will test whether the judgement is worth that cost.

The question behind the measurement

Shared Memory is an open-source memory framework that lets coding agents store and search facts, decisions, and retrospectives with their provenance, shared across projects. Its vector search returns the records closest to a question, and its reranker (a second-stage scoring model that reorders vector-search candidates) orders them by how well their wording matches. Neither step says whether the records actually contain enough information to answer the question. That property is called sufficiency, and today only the agent reading the results judges it. This pilot asks whether GLiNER2.5-Decide, a small local classifier, can make that sufficiency judgement for each search. The classifier would leave the search results and their order unchanged, adding a verdict to each response. If it proves useful, it becomes an optional component, switched on in .env and shipped as its own Docker image.

Two things must be shown before any installation runs the verifier, namely that the verdict is accurate and that it is worth the machine's resources. Installations differ widely; the project's test machine, the testbed, is a six-core Intel Core i5-9400F with no spare GPU. This page covers the second question on one well-equipped workstation, while the first question remains open. We found no published evaluation that tests whether a passage answers a question for Decide, for TypeSafe's hosted Jev decision model, or for JevK5, an open reproduction of Jev that Decide's maker, Fastino, compares with Decide on its own benchmark in the model card. Their reported results cover routing, entity resolution, and checking extracted facts. Until the accuracy study runs, "Decide judges sufficiency" remains an untested hypothesis.

Setup

Host
AMD Ryzen 9 5900X, 12 cores and 24 threads, 62 GiB RAM, Linux 7.2.13-200.fc44.x86_64. CPU governor powersave with boost disabled; the sustained clock frequency was not recorded.
GPU
Intel Arc Pro B70 (Xe2, 31.9 GiB), idle and drawing no display. The framework's own encoders (the embedding and reranking models that turn text into vectors and score candidate records during every search) run on a separate Arc B580, which the pilot never touched.
Model
fastino/GLiNER2.5-Decide at revision 9d1bfb8, with 486,444,053 parameters, of which 433,921,024 sit in its DeBERTa-v3-large encoder. The model card advertises 340M parameters; we have not reconciled its counting convention with the loaded count.
Software
Three Docker images on one pinned fedora:44 base, all with torch 2.14.1, covering CPU (1.92 GB), XPU for SYCL (11.32 GB), and Vulkan (2.95 GB) with IREE 3.13 (an ahead-of-time compiler that translates neural networks into GPU compute shaders). Drivers used Mesa 26.2.6 (Vulkan) and Intel compute runtime 26.35 (Level Zero, Intel's low-level GPU driver interface).

Five configurations

  • CPU, 6 threads runs torch in fp32 (single-precision floating point) on six physical cores.
  • CPU, 12 threads runs torch in fp32 on all twelve physical cores.
  • B70 SYCL fp32 uses torch's XPU backend, which runs Intel C++/SYCL compute kernels on Level Zero in single precision.
  • B70 SYCL fp16 uses the same XPU and SYCL stack with weights and activations in fp16 (half-precision floating point).
  • B70 Vulkan fp32 runs the encoder compiled ahead of time by IREE to cross-vendor Vulkan compute shaders while the tokenizer and output heads stay on the CPU.

Each tested configuration is called an arm of the benchmark. The GPU arms drive the card from six CPU cores. Because the five configurations vary in numerical precision, compiler stack, and input-shape handling as well as hardware backend, the comparisons below evaluate complete deployable configurations and attribute a difference to a backend only where the data isolates that cause.

A workload taken from real searches

The benchmark measures two workload tiers. The first tier times end-to-end sufficiency verdicts on synthetic searches matched to real search lengths, and the second tier times isolated encoder prefill (the bidirectional encoder's forward pass across a batch of input token windows to produce contextual hidden states) on fixed grids of seeded random tokens.

We took token counts from twenty real searches on the workstation's memory, with ten results each, to set the end-to-end workload sizes, and discarded all record text. The median result was 611 tokens long. Searches fell into two length groups, as 11 of the 20 returned 4,398 to 10,540 tokens in total and 9 returned more than 20,000 because a single long record can run to 51,334 tokens. We rebuilt three searches with public text from the framework's README at those exact lengths to represent the upper-middle search (10,540 tokens, called typical below) and two tail searches, one near the 90th percentile (49,508) and the largest (59,593).

Each verdict follows the library's own long-text path. The library cuts every result into 384-word windows that overlap by 64 words, scores all windows of the search in batches of eight, and assigns each result the highest "states the answer" probability across its windows. For the typical search, that requires 5 encoder calls and 15,484 tokens of prefill. On the tail searches, windows reached 543 tokens; the encoder's relative position scheme accepts that length, whereas a backend compiled for fixed shapes must compile for the longest window it will meet.

How each number was measured

Replication
The measurements come from two rounds. Round one supplied the CPU prefill figures and the typical-search and single-result times. Round two, which ran after an independent review with stricter checks and matched timing boundaries, supplied the GPU prefill figures, the tail searches, the memory figures and the effect on the framework. Every block runs in a fresh container. The B70 arms ran four prefill blocks and two service blocks in alternating order; the CPU arms ran two of each. Tables give the median of the block medians with the range between blocks in small type, because container-to-container variation between blocks represents the uncertainty that matters for a deployment rather than call-to-call scatter inside one container.
Time to verdict
Wall-clock time from sending a search's results to the service over HTTP on the same machine to receiving every probability back. A classifier returns one complete verdict instead of streaming tokens, so for a decision model the time to first token and the time to the full answer are the same. The largest median residual between the client's request time and the server's scoring time was 20.2 ms; single residuals reached 50.2 ms. Round-one client timings include parsing the JSON response; round-two timings stop after reading the response body, before parsing. Both exclude preparing the request. Each block timed ten requests per workload, except that the CPU arms timed three on the 90th-percentile search.
Prefill
The encoder's forward pass at fixed batch and length, on seeded random tokens drawn on the same batch-and-length grid. The round-two GPU arms share identical arrays; the CPU figures come from round one and use a different seeded draw. Two boundaries are timed. Device starts with the inputs already on the processor that computes and stops when the result is complete there. Host to host starts from CPU arrays and stops when the hidden states are back in CPU memory. On the CPU these are the same work. On the B70 they differed by at most a few percent, so the tables give the device figure. The GPU arms made three warm-up calls and fifteen timed calls per cell; the CPU arms made two and ten.
Memory
Host RAM is sampled every 50 ms from the container's own Linux control group (cgroup, the kernel's per-container resource tracker). We report three figures: anonymous memory (heap and tensor allocations in RAM, excluding cached files) when the model is loaded before serving any request, anonymous memory when idle after work, and the cgroup's lifetime high-water mark, which includes model loading and file cache. VRAM is read in step from the kernel's per-client counters for the B70 (drm-total-vram0).
Effect on the framework
The harness timed the same twenty searches three times per block, once before the verifier started, once while the verifier judged the typical search back to back with no pause, and once after the verifier stopped. Each search's latency under load is divided by the mean of its own before and after times. This captures the worst case of a saturated verifier rather than the cost at an everyday request rate.
Safety
Before starting each round-two container, the harness verified that both device nodes matched the B70's PCI address, that no GPU client visible to the benchmark's Linux user held memory on the card, and that the card's other user, a local builder seat (a local LLM coding assistant that uses the B70 when this benchmark is not running), was idle. During each run, sampled telemetry visible to that Linux user killed the container if host memory fell below the room the framework's own services need to reach their caps, or if the card passed the builder seat's 28 GiB cap. None of the 42 measured containers tripped either limit.

Results

Time to verdict

For a typical search, the B70 answered in 0.663 s with SYCL fp16, 1.32 s with SYCL fp32, and 2.02 s with Vulkan. Twelve CPU threads needed 44.2 s and six needed 50.1 s. On the 90th-percentile search, the CPU took 196 s, more than three minutes for a single verdict, while the card took 2.84 s with SYCL fp16. The largest search was measured on the card only, finishing in 3.47 s with SYCL fp16.

On a single 384-token result, Vulkan took 0.383 s, which is 7 times slower than SYCL fp32. IREE could not compile this encoder with variable shapes, so the Vulkan service holds one fixed-shape module and pads every call to match it. Round one used an 8 × 512 module for the single-result and typical-search runs, and round two an 8 × 576 module for the tail searches. Scoring one result therefore costs as much as scoring eight, and on the two tail searches padding filled about a quarter of the executed token slots.

Prefill speed

Isolated encoder prefill helps explain the end-to-end verdict timings. At batch 8, the CPU sustained 401 to 783 tokens per second on twelve threads (654 ms at 8 × 64 and 10,211 ms at 8 × 512). On the B70, SYCL in half precision reached 46,955 tokens per second (43.6 ms) at 8 × 256 and 34,046 tokens per second (120 ms) at 8 × 512; in single precision it peaked at 20,462 tokens per second (50.0 ms at 8 × 128) and needed 311 ms at 8 × 512. Vulkan held between 10,743 tokens per second (381 ms at 8 × 512) and 12,325 (83.1 ms at 8 × 128). At the largest cell, the card is 85 times faster than twelve CPU threads with SYCL fp16, 33 times faster with SYCL fp32, and 27 times faster with Vulkan.

At batch 1 the SYCL timings barely change with size. The smaller SYCL cells had median timings of roughly 43 to 47 ms until the work grew past 512 tokens per call in fp32 (8 × 64) and past 2,048 in fp16 (8 × 256). That plateau suggests a large fixed cost per call; kernel launches and host-side dispatch on a CPU without boost are likely contributors, but this benchmark did not profile them. The tested Vulkan path, compiled ahead of time into a single module, showed no comparable plateau and finished a 64-token call in 14.5 ms. At 8 × 64, SYCL fp32 (45.6 ms), SYCL fp16 (44.4 ms) and Vulkan (43.1 ms) take about the same time; above that size, both SYCL configurations pull ahead.

Effect on the framework's own searches

While a CPU verifier ran continuously back to back, the median per-search latency increase across the paired searches from both service blocks was 12.5% with six threads and 41.9% with twelve, consistent with contention for shared host resources. With each B70 configuration the median paired increase was below 1%, within the noise of the paired baselines, although single searches varied more. One six-thread block overlapped a scheduled consolidation run (Shared Memory's background job that folds stored records into summaries); its median ratio (1.14) stayed close to the other block's (1.12).

Do the backends give the same answer?

On twenty pairs of real question and text, every configuration's probabilities matched the CPU fp32 reference within 0.0007, with the largest gap belonging to SYCL fp16, while the single-precision GPU arms matched within 0.0000035. Intermediate encoder hidden states diverge more than the final probabilities. On random tokens the fp32 backends stayed within 0.09 of the reference, while fp16 drifted by up to 7.9 on values that reach about 20. DeBERTa models are sensitive to half-precision arithmetic. The final probabilities absorb that drift on real text here, but the accuracy study must use the precision that would ship.

How far the numbers can be trusted

Solid

  • Every round-two block reports valid status, and inspection found the expected counts in every prefill output; no run was excluded.
  • B70 timings repeated closely across blocks, differing by at most 7.0% on the large cells and 8.7% overall.
  • The differences between CPU and GPU are tens of times larger than any spread measured.
  • Code, inputs, model, images, and compiled modules are hashed into a manifest for every round-two block.

Limits

  • Round-one service containers were stopped by force after measurement, as designed, and carry the earlier harness's weaker checks.
  • Measurements come from one machine with CPU boost off. The CPU arms varied by up to 30% between blocks and had two blocks each.
  • Text was public README prose cut to real lengths. Real records with code or tables may produce more tokens per window.
  • Vulkan ran through IREE with the turing preset; IREE has none for Intel. In a one-shape trial (1 × 128, recorded in bench/vk/preset_trial.md), four presets gave correct output and turing tied with ampere as the fastest. A tuned Vulkan path could do better.
  • VRAM counts are sampled per client and show only clients this user can read. The card was otherwise idle.
  • Framework interference was measured under continuous saturation rather than at a typical request rate.
  • Nothing here measures whether the verdicts are right.

CPU or GPU

On this workstation, SYCL fp16 on the B70 added about 0.66 seconds to the typical search and about 3.5 seconds to the largest, which may suit a workflow where an agent waits for the verdict. Memory stayed within a few GiB, and the framework's median per-search latency increase stayed below 1%. SYCL fp16 is the fastest configuration for real searches. Vulkan, measured only in single precision, is the fastest backend for small single calls and about a fifth slower than SYCL fp32 at 8 × 512; serving single results efficiently would need a different shape strategy, such as smaller static modules or variable shapes.

The CPU makes the same verdict expensive. Forty to fifty seconds for a typical search and three to four minutes for a long one rule out a verdict that an agent waits for. Running the verifier continuously also raised the framework's median per-search latency by 42%. The six-core i5-9400F testbed was not measured, so its performance is unknown and nothing here should be scaled to it. On this evidence a CPU deployment fits best where verdicts are computed in the background, off the search path, or for short results alone.

Testing whether the verdict is worth having

The accuracy study will put each search to three judges, comparing the reading model alone (R), Decide alone (G), and the reading model shown Decide's probabilities (RG), while the reranker score (A) stays as the free baseline for Decide. The study fixes sixty questions in advance, mixing answerable ones with questions the memory does not answer, including ten traps with a near miss such as the wrong host or a negated statement. Each question is asked in five phrasings. Two independent model judges label every search, and the project's maintainer labels a random sample of 100. If the maintainer and the judges agree less than Cohen's κ = 0.6 (a chance-corrected measure of inter-rater agreement), the study draws no conclusion.

Comparing accuracy across judges looks like a job for analysis of variance, but ordinary ANOVA fits this design poorly. Each verdict is right or wrong, the same questions appear under every judge, and the five phrasings of one question are correlated, while ordinary ANOVA assumes continuous, independent errors with equal spread. ANOVA on such proportions can show effects that are not there even after the usual arcsine transform (Jaeger, 2008). Instead, the study uses five procedures.

  • Primary test. A logistic GEE (Generalized Estimating Equations) regression model for binary outcomes clustered by question, with the Mancl–DeRouen small-sample covariance correction, compares the reading model with Decide's probabilities (RG) against the reading model alone (R) and Decide alone (G) against the reading model alone (R). Holm's method (a step-down multiple-testing adjustment) controls the false-positive error across the two comparisons. A plain McNemar test ignores that pairs from one question are correlated and can give invalid inference here; corrected versions exist for clustered pairs (Obuchowski, 1998; Durkalski et al., 2003).
  • Confirmation. A sign-flip permutation test on the per-question differences, which assumes those differences are symmetric when there is no effect, and a bootstrap that keeps the mix of question types check the primary test.
  • Does the effect differ by question type? A permutation test shuffles the question-type labels, assuming the per-question differences are exchangeable across types. In simulations where question types are exchangeable, the GEE interaction test rejected 8.0% (no effect) and 16.5% (an equal effect in every type) of datasets at the 5% level, against 3.75% and 4.0% for the permutation test.
  • Sensitivity. A Bayesian logistic mixed model in bambi (a Python library for fitting Bayesian generalized linear mixed models), read as the difference in accuracy averaged over the questions, checks sensitivity to model assumptions.
  • What the errors are. False "answered" verdicts on searches that do not answer are reported apart from false "not answered" verdicts, because false "answered" verdicts mislead the agent.

The power simulation runs that exact procedure, 200 simulated datasets per scenario. With no true effect, the Holm-adjusted RG-against-R comparison rejected 1.5% to 4.5% of datasets and either comparison rejected 3% to 7%, close to the nominal 5%. How large a gain sixty questions can detect depends on two unmeasured inputs. The first is how often the reader is right on its own, modelled as a baseline probability before question and phrasing effects. The second is how often the reader with Decide simply repeats its unassisted verdict, modelled as a copying probability; when it does not copy, the simulation draws a fresh verdict, so the agreement between the two is higher than the copying probability. At a 75% baseline and a copying probability of 0.8, estimated power was 82.5% for a 4.05-point gain; at 0.5 it was 91% for a 7.84-point gain. Copying also caps the possible gain, which is why the curves flatten. These are provisional planning figures; they assume sixty independent evaluation questions and do not yet simulate fitting Decide's probability threshold or questions that share records. Before the study runs, the maintainer must also state what gain would justify adopting Decide, because a non-significant result does not show that Decide is as accurate as the reader.

Reproducing this

The scripts and every block's raw output and manifest are kept with the study. The archived outputs support recomputing the benchmark summaries with bench/analyze2.py. The statistics scripts separately produce the power and calibration results. From the argon folder, assemble.py combines the corrected text with the archived charts; it does not redraw them. The build and measurement commands below are illustrative and need the full recorded image digest and a chosen backend. Model weights are pulled from Hugging Face at revision 9d1bfb848cd1 (SHA-256 40a5a23ff860dc3d…). The CPU and GPU images are built from sha256:15da97ed9aa9….

docker build --build-arg BASE=fedora@sha256:<recorded digest> --build-arg BACKEND=<cpu|xpu|vulkan> -t sv-bench:<backend> .
bash run_all.sh                     # round 1: two passes, five configurations
bash run_all2.sh                    # round 2: independent blocks, matched timing boundaries
python analyze2.py                  # benchmark summaries (bench/out/results2.json)
python ../stats/sufficiency_stats.py power > ../stats/power.json   # power simulation
python ../stats/calib_interaction.py; python ../stats/calib_perm.py  # calibration
cd ../argon && python assemble.py      # this page from the corrected text and archived charts
