# Run the A770-builder Lean comparison

## Question and why it matters

Using the shipped Intel Qwen3-Coder-30B-A3B-Instruct INT4 AutoRound B70 profile, does giving the builder a formal Lean contract or access to a dedicated proof-feedback helper increase the proportion of bounded patches independently accepted at the same resource limits? Does it improve behavioral correctness without making the code harder to maintain or the workflow disproportionately expensive?

The kit audit compared graders on a patch the model had already written. This experiment changes what the model receives before and during generation. If a formal contract alone helps, the skill could gain without an interactive prover dependency. If feedback adds value, its benefit must justify checker, model, and reviewer costs. The first comparison uses Lean-native tasks so proof feedback concerns the delivered function directly. A later polyglot kit experiment can compare native invariant checks and a proved reference on the actual foreign-language outputs. Its result is behavioral evidence on exercised inputs.

## Freeze the setup before scoring

- Use repository profile `intel-qwen3-coder-30b-a3b-w4a16-vllm`, checkpoint revision `2e34fa861568584540b3c4f7a47cc1a4a4d88773`, the recorded B70 recipe, and a single pinned OpenCode version. Record checkout commit, exact profile hash, backend/image identity, Lean/Lake archive digest, compiler command, effective sampling parameters, and cache/reset policy. Use the same settings in every arm. Pair seeds where the backend honors them and record evidence of support. Otherwise use independently initialized sessions and pair by task/repetition.
- Freeze eight reviewed tasks and their standalone baseline commits. Candidate roster: longest affordable prefix, log-count aggregation over normalized rows, minute selection with ties, interval coalescing, stable deduplication, sorted merge with multiplicities, bounded state transition, and a routine field projection as a low-benefit comparison. The roster is a proposal until the exact contracts, edit scopes, public examples, and graders are signed off. Use the existing `takeBudget` contract for the first engineering rehearsal. Rehearsal attempts are excluded from the study. Keep the proved sample implementation and private article out of all seats.
- For each scored task freeze the prose contract, frozen Lean proposition, allowed source files, compiler command, public examples, hidden behavioral tests, and blind rubric. Hash them before candidate collection. Use known-good and deliberately faulty controls to validate the graders, including a fault public tests miss. Record false accepts and rejects. Freeze hidden test inputs outside the candidate seat.
- Proposed starting limits for preflight: 900 seconds of builder wall time, 600,000 cumulative prompt-plus-completion tokens, at most 12,000 cumulative completion tokens, and a 4,096-token per-response ceiling. These are design choices to validate on unscored rehearsals. Publish the final values in the manifest before scoring, then apply them identically. Bill cached prompts at their logical token count. Count reasoning once when included in completion usage.
- Validate the backend budget control before scoring. Use trustworthy counts for fully rendered requests, reserve each request's prompt tokens and allowable completion before it reaches the backend, and enforce the remaining completion grant upstream. Charge retries and tool context. Check missing or cancelled usage, concurrent requests, and count mismatches. Treat untrustworthy metering as infrastructure invalidation and retain its evidence. A per-response ceiling or a post-run tally alone cannot enforce the cumulative limit.
- Validate an equivalent compiler path for A, B, and C. Offer only C a reviewer-owned offline proof helper that links the frozen obligation to the candidate function and returns goal or proof diagnostics. All arms retain the ordinary Lean compiler, which itself can give proof diagnostics if a builder writes an example or theorem. Define C minus B as the intent-to-treat effect of offering the helper. Record organic proof use in every arm. A or B reaching the dedicated helper is contamination, as is A seeing the frozen theorem. Before scoring, show that C can use the helper, that A and B cannot invoke it, and that common build and public-check commands behave identically. Keep scratch proofs outside the final implementation patch. Record proof attempts and the diagnostics actually surfaced. Grade optional proof artifacts separately using reviewer-controlled theorem identity and axiom policy. Never use a candidate-controlled success flag as proof.
- Use clean standalone seats, fresh histories, identical allowed tools apart from the intervention, and no network beyond the designated model bridge. Before scoring, complete one unscored A/B/C rehearsal through blind patch replay and cost export. Keep its exact manifest and invocations. Exercise quota exhaustion and timeout with recoverable capture. Verify that the proof checker rejects a placeholder, unapproved axioms, a weakened proposition, and a proof about the wrong function. Verify that C diagnostics link to the current candidate revision.

## Builder prompt

Give every builder the following core prompt with the bracketed fields filled from the frozen task manifest:

> Implement [FUNCTION AND SIGNATURE] in [ALLOWED SOURCE FILE]. The input domain, required outputs, edge cases, and caller expectations are [FROZEN PROSE CONTRACT]. Work in this standalone seat and modify only the named implementation source. Use [IMPLEMENTATION COMPILER COMMAND] and [PUBLIC EXAMPLE COMMAND] to check your work. The deliverable is the implementation patch. Stop when the implementation is ready within the supplied attempt limits. Report the files changed and the public check result.

- A receives only the core prompt and the common task materials.
- B appends: “The reviewer’s formal contract is [FROZEN LEAN PROPOSITION]. Use it as a reference for the intended behavior.”
- C appends the B paragraph plus: “You may run [REVIEWER-OWNED PROOF COMMAND] on scratch attempts to inspect proof obligations and goal diagnostics for your implementation. Scratch proofs are optional and outside the required patch.”

Keep the substantive behavioral requirements equivalent across arms. A missing requirement in the prose would confound the effect of formalization with extra information. Keep the private graders and prior solutions inaccessible to the model.

## Run and grade

Use five matched repetitions per task, 40 attempts per arm and 120 attempts overall. The proposed wall cap implies up to 30 serial builder-hours before rehearsals and reruns. Record a seeded randomized task/block order and randomize A/B/C order within blocks. Give each attempt its own fresh seat and opaque ID. Reapply the captured patch to the frozen base for grading. Run behavioral grading independently of the proof outcome and public grade so a proof failure cannot suppress the primary outcome. The primary pass is mechanical: a present implementation patch, declared edit scope, clean application, and all frozen hidden checks. Blind human findings do not veto the primary pass. Rate maintainability and contract fidelity separately using prespecified categories (no finding, minor, material) with examples and an adjudication rule frozen before scoring. Count identical patches as separate assigned attempts. For exact duplicates, reuse the blind rating and report separately how often the reviewer did fresh work. Keep reviewers blind to arm, timing, and proof transcript when they judge the implementation. Report grader disagreements and how they were resolved. Classify missing deliverables and effective budget exhaustion as unsuccessful attempts. Assign exactly one official outcome per scheduled slot. A complete original block is official. If infrastructure invalidates any slot, retain the original block and rerun the whole block once with the same assignment and fresh seats after resolving the cause. A complete valid rerun replaces all three original outcomes, including the original valid siblings. If that rerun is also invalid, retain the original valid outcomes and mark the original invalid slots unresolved. Publish the effective 40 assigned slots per arm, the resolved denominator, complete-pair counts, and worst/best bounds that allow every unresolved slot to be a pass or fail. Keep contaminated runs in the assigned-arm analysis and show sensitivity excluding affected blocks. Record all discarded runs and include their cost in a separate total experiment cost.

## Measure, analyze, and decide

- Primary measure: independently accepted implementation patches per assigned attempt, with valid-run counts and invalidations disclosed. Main contrasts are B minus A (contract context) and C minus B (prover feedback). Report each task's both-pass, first-arm-only pass, second-arm-only pass and both-fail counts, then the paired percentage-point difference and 95% interval. Treat the eight tasks as a fixed roster and give them equal weight. For complete data, compute a conditional 95% percentile interval by resampling whole matched repetitions within each task, five with replacement, for 20,000 seeded bootstrap draws. Aggregate equally over the eight tasks in each draw. For missing data, report complete-pair estimates by task with their counts and worst/best bounds for the assigned contrast. Any complete-pair interval resamples the available pairs per task and describes only the resolved subset. Suppress it when a task has no complete pairs. Flag small per-task sample sizes and degenerate bootstrap intervals, which do not establish equivalence. Show all task differences and leave-one-task-out sensitivity. The interval describes repetition-level uncertainty for this fixed task mix under independent blocks within task. It does not generalize to unseen tasks. Treat both contrasts as exploratory in this pilot.
- Secondary measures: proof attempted, produced, and independently accepted among attempts with and without scratch output, hidden behavioral failure categories, blinded review results, timeouts, token-limit stops, infrastructure failures, prompt/completion/optional reasoning counts, builder wall time, checker CPU time and aggregate peak memory, contract preparation and reviewer minutes. Report medians and ranges and all p95 sample sizes. Report incremental proof-helper setup and reusable contract preparation separately from recurring checker and reviewer cost. Count recurring reviewer minutes on unsuccessful patches too. Report cost per accepted patch as total official arm cost including unsuccessful attempts divided by accepted patches. If an arm has zero passes or the comparator cost per accepted patch is zero, report the relevant cost or relative ratio as undefined.
- Before collecting results, freeze these provisional thresholds or document any agreed change: at least four net additional accepted patches per 40 matched attempts (+10 points) over the comparator, no more than 20% extra tokens and 20% extra wall time per accepted patch, checker p95 at most 5 CPU seconds and 1 GiB aggregate peak memory, plus at most 5 extra reviewer minutes per patch and 30 minutes per task for contract preparation/review. Meeting a point threshold with a wide interval supports replication, not a definitive claim. Report null, negative and inconclusive findings.
